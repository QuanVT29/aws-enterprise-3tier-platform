# Site Reliability Engineering (SRE) Incident Response Runbook

## 1. Overview & Escalation Severity Matrix

This runbook defines operational guidelines and triaging steps for on-call engineers responding to automated alerts generated by CloudWatch Alarms within the primary production ecosystem.

| Severity | Impact | Notification Channel | Response SLA |
| :--- | :--- | :--- | :--- |
| **SEV-1 (Critical)** | Outage / Canary Availability < 100% | PagerDuty / SMS / Voice / SNS High | < 15 minutes |
| **SEV-2 (High)** | Cluster CPU > 80% / Elevated HTTP 500 | Slack #incidents / Email Alert | < 30 minutes |
| **SEV-3 (Moderate)** | Memory Saturation > 75% / Latency Warning | Slack #telemetry-alerts | < 2 hours |

---

## 2. Standard Operating Procedures (SOPs)

<a id="high-cpu"></a>
### SOP-01: High CPU Saturation (`Enterprise-App-HighCPU-Alarm`)

#### Symptoms
- Alarm State: `ALARM` on metric `AWS/EC2/CPUUtilization > 80%`.
- User-perceived latency degradation or request throttling.

#### Triage Steps
1. Navigate to **CloudWatch Dashboard** $\rightarrow$ `Enterprise-Primary-Observability-Hub` to observe traffic concurrency vs CPU spike.
2. Establish a Zero-Trust terminal session into one of the affected nodes via SSM:
   ```
   aws ssm start-session --target <INSTANCE_ID> --region ap-southeast-1
   ```
